0 · 已暂定的决策

核心原则（v0.4）：默认完全隔离——每个资源只属于一个租户（模型 Key、助手、知识库、成员等），不跨租户共享。唯一例外是 LensNode：支持「私有节点」和「共享节点」两种。共享节点归超级管理员管辖，由超管设置对哪些租户可见（白名单 / 黑名单二选一）。超管是「平台租户」，自己的资源与别的租户规则相同。其他资源以后若要共享，走「所有者租户显式授权」。
#问题暂定
1用户是否多租户数据模型支持多租户成员；界面第一版单租户，仅超管有租户切换器
2模型来源租户自有：每个租户配置自己的模型 Key；不提供平台全局模型
3通知渠道平台提供默认渠道；租户可配置自己的飞书等渠道
4租户内角色租户管理员（管理租户内一切）/ 成员；暂不设「资源管理员」，后续按需再拆
5超管看租户数据默认不可；须点「进入租户」，进入期间顶部常驻红色提示条，全程审计
6节点两种并存：①私有节点——租户自己注册、自己运维；②共享节点——超管注册与运维，按可见范围（全部租户 + 黑名单，或仅指定租户 = 白名单）开放给租户使用

3.4 · 超级管理员的职责边界与「代管」（v0.6 新增）

超管关心 / 要控制的
  • 全局与租户级统计：租户数、活跃度、提问量、模型用量（只看汇总）
  • 节点与全局配置：共享节点及其可见范围、全局配置、任务调度
  • 官方目录：上传 / 发布技能、MCP、连接器
  • 模型：只看统计；另留「平台模型配置」，仅供平台自身功能使用
  • 告警与通知：平台自己的订阅、渠道、记录（自己通知自己）
  • 租户：创建 / 停用租户，以及「代管」
超管不关心 / 不参与的
  • 助手的创建流程、Run 的运行状态（平台视角不出现）
  • 租户的用户、用户组、角色与权限：由租户自己控制，代管模式下也不可见
  • 租户的对话内容、环境变量值、私有节点
代管：超管可以「进入租户」，帮它建立模型与各类配置（模型、节点、知识库、助手、技能 / MCP / 连接的启用与环境变量等），进入后顶部显示红色代管提示条，全程审计；但成员、用户组、角色三类页面在代管模式下不可见。租户创建向导里可以选「由我代管配置」或「交给租户管理员自己配置」。

3.5 · 资源目录与环境变量（v0.5 新增）

代码现状（已核对）：Skill、MCPServer 都是「全局资源」，没有租户字段；EnvironmentVariableSet 是加密的、名称全局唯一的变量集，只有管理员（staff）能增删改，并有「显示明文」接口；助手通过 AssistantSkill / AssistantMCP 的 environment_variable_set 把变量集绑定到具体技能 / MCP；技能 / MCP 自己声明需要哪些变量（definition.environment / environment）。多租户化时这三处都要加租户归属。

资源谁发布 / 维护租户能做什么与租户自有内容的关系
官方技能 / MCP超管（平台「官方目录」）启用即直接使用（引用，不复制）；自动跟随更新；重大变更需租户确认；环境变量不在启用时填，而是配置助手时按助手绑定变量集租户侧分「平台官方」「我的」两个标签，严格分开
租户自有技能 / MCP租户管理员（上传 / 接入）完全自主，仅本租户可见放在「我的」，与官方互不混合
连接器超管（官方发布，含允许访问范围）选择官方连接器 + 填写自己的凭证；不能上传自建连接器没有「我的连接器」

环境变量分三层

层内容谁维护谁能看值
① 声明这个能力需要哪些变量（名称、说明）发布者：官方内容归超管，自建内容归租户—（只是名字）
② 平台托管值（可选）平台统一提供的凭证，如平台统一采购的搜索服务超管只有超管；租户只看到「平台托管」，不能查看、不能覆盖
③ 租户自己的值租户自己的 Token、地址、账号（现在的 EnvironmentVariableSet）租户管理员（租户侧「环境变量」页；也可在配置助手时直接选择 / 新增）仅本租户管理员（显示明文要记审计）；超管也看不到
结论：环境变量「声明」和「平台托管值」由超管维护；租户自己的凭证值必须由租户自己维护，不应该交给超管——否则平台就持有了所有租户的密钥，违背隔离原则，也是安全风险。租户在配置助手时配置自己的技能与环境变量，与你的想法一致。

4 · 三区划分原则

① 工作台

所有人。DeepSeek 式极简：会话列表 + 居中阅读 + 输入框。沿用四种风格（经典 / 暖纸 / 极简 / 紧凑）。

② 租户管理

租户管理员。嵌在用户侧，参考图 2 的「空间 / 组织」与图 3 的市场：概览 → 助手 → 数据资产 → 市场 → 成员 → 节点 → 审核 → 用量。卡片、搜索、已安装、一键添加。

③ 平台控制台

仅超管。与其他区域同风格、明亮不压抑：租户、共享节点、汇总用量、任务、通知底座、全局配置、审计。更密、更偏表格。

判断口诀：只影响单个租户、有业务语义 → ②；跨租户、涉及基础设施、风险高 → ③。

7 · 租户生命周期

创建（超管向导） → 待激活（已邀请管理员，未登录） → 正常 → 额度告急 / 超额 → 已停用（只读 / 禁登录） → 已归档（保留期后删除）

创建向导 5 步：基本信息 → 额度（成员数、助手数、存储）→ 初始管理员 → 初始配置（可由超管代配模型与节点，或交给管理员上手引导）→ 确认。

8 · 治理新增的边界场景（将在原型中逐一实现）

租户侧
  • 新租户全空：引导三步（连知识库 → 建助手 → 邀成员）
  • 额度用完 / 80% 预警 / 模型被平台下线
  • 新租户尚无私有节点、也未被授权共享节点：助手不可用，引导去注册节点或联系超管
  • 共享节点：从白名单移除租户 / 加入黑名单时，预览受影响的助手并给出过渡期；节点下线对多租户的级联影响
  • 同一共享节点上多租户并发：可选的每租户并发上限；各租户 Run 与工作区在节点上互相隔离
  • 节点全部离线 / 模型 Key 失效：助手提示与管理员告警
  • 管理员被降级后正在编辑的页面 → 即时无权限
  • 最后一个管理员不可被移除 / 降级
  • 市场模板版本更新，已安装副本提示可升级
  • 成员 0 / 3 / 上千；助手 0 / 3 / 上百
平台侧
  • 租户 0 / 3 / 上百，状态筛选与分页
  • 停用租户时的影响面确认（成员数、运行中 Run、分享链接）
  • 进入租户：顶部红条、仅限时、审计留痕、退出
  • 租户名 / 域名冲突；初始管理员邮箱已存在于其他租户
  • 汇总用量：只展示各租户数量与费用，点击不进入内容
